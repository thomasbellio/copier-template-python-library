# Implementation Brief: Agent Harness for `copier-template-python-library`

**Target repo:** https://github.com/thomasbellio/copier-template-python-library
**Audience:** a coding agent making the changes locally, with the owner reviewing.
**Date:** 2026-11-24

---

## 1. Goal

Add an "Agent Harness" to the copier template so every generated Python project ships with:

1. A set of maintainability checks that run only against **new or changed code**.
2. An `AGENTS.md` that tells any coding agent how to work with those checks.
3. Thin adapters that wire the checks into Claude Code hooks, lefthook and GitHub Actions.

The checks must give agents fast, deterministic, actionable feedback. They must not push agents into whole-codebase refactors.

### Definition of done

- A project generated with default answers passes every gate on its initial commit.
- The scenarios in section 13 produce the stated pass/fail results.
- `AGENTS.md`, `CLAUDE.md`, `.claude/`, the harness scripts and all tool configs are generated by the template.
- A retrofit guide ships with the template (section 12).

## 3. Decisions already made

These are settled. Do not reopen them.

1. **Checks live in agent-agnostic scripts.** Agent hooks, lefthook and CI are thin adapters that call the same entry point.
2. **Scope is changed code only**, measured against the merge-base with the default branch (section 5).
3. **The Claude Code `Stop` hook blocks** when the gate fails, with one forced retry, then reports to the human instead of looping.
4. **Semantic duplication is advisory**, never a hard gate (section 7.11).
5. **Agents refactor opportunistically**: fix what they touched, never the whole codebase.
6. **`AGENTS.md` is the canonical instruction file.** Claude-specific files only point to it or adapt it.
7. **Agents never stage or commit unless the user asks.** They leave changes unstaged for review and propose a commit message instead.
8. **Change records follow existing standards:** Keep a Changelog and Semantic Versioning (already in the template), Conventional Commits, a regression test per bug fix, a selective troubleshooting log, and ADRs for design decisions.

Tool selection, as chosen by the owner:

| Concern | Tool |
|---|---|
| Cognitive complexity | complexipy |
| Size and shape limits | Ruff `PLR09xx` |
| Architectural boundaries | import-linter |
| Coupling and cohesion | pyscn |
| Dead code | vulture |
| Mutation testing | cosmic-ray |
| Exception hygiene | Ruff (`BLE001`, `S110`, `S112`, `TRY`, `B904`, `B012`, `E722`) |
| Type precision | mypy |
| Docstrings | Ruff `D1xx` requires them; pydoclint checks they match the signature |
| Churn × complexity | git history plus complexipy |
| Semantic duplication | pyscn clone detection (advisory) plus an `AGENTS.md` rule |

## 5. Scope model: what "changed code" means

Implement this once, in `scripts/harness/scope.py`. Every runner uses it.

### 5.1 Base ref resolution

Resolve in this order and stop at the first that works:

1. `HARNESS_BASE` environment variable.
2. `git merge-base HEAD origin/<default_branch>`.
3. `git merge-base HEAD <default_branch>`.
4. If `HEAD` is the default branch, or no merge-base exists: `HEAD` (uncommitted changes only).
5. If the repo has no commits: the empty tree, so everything counts as new.

`<default_branch>` comes from the copier answer and is written into `harness.toml`.

### 5.2 Changed set

Diff the base against the **working tree**: committed, staged, unstaged and untracked `.py` files under `src/` and `tests/`. Produce, per file, the set of added or modified line numbers.

### 5.3 Touched definitions

A finding is **in scope** if either holds:

- It sits on a changed line.
- It sits anywhere inside a function, method or class whose line span contains at least one changed line. Use the innermost enclosing `def` for function-level findings and the enclosing `class` for class-level findings (CBO, LCOM, public-method counts). Compute spans with the stdlib `ast` module.

This is deliberate. A finding such as "too many statements" is reported on the `def` line, which may not be a changed line. Line-only filtering would let an agent grow a bad function forever. With span-based scope, touching a function makes the agent responsible for that function and nothing else.

New files are entirely in scope.

### 5.4 Whole-project checks

import-linter and dependency-cycle detection cannot be scoped to a diff. They run on the whole project and must always pass. Existing projects grandfather violations in config (section 12).

## 6. The entry point: `scripts/check.sh`

A thin shell wrapper around `python scripts/harness`. The Python code uses the standard library only.

| Invocation | Used by | Behaviour |
|---|---|---|
| `scripts/check.sh --file <path>` | PostToolUse hook | Fast checks for one file. Budget: 2 seconds |
| `scripts/check.sh` | Stop hook, lefthook, CI, agents | Full gate on the changed set. Budget: 30 seconds |
| `scripts/check.sh --mutation` | CI job, on demand | cosmic-ray on changed lines. Slow |
| `scripts/check.sh --all` | Humans | Whole-codebase audit. Report only, always exits 0 |

Requirements:

- **Exit codes:** 0 pass, 1 gate failed, 3 harness or tool error. Adapters translate these; the script itself knows nothing about Claude Code.
- **Run all checks**, then report. Do not stop at the first failure. Run independent tools in parallel.
- **A missing tool is exit 3**, never a silent pass.
- **No changed Python files** means print one line and exit 0.
- **Output format**, plain text with no colour codes when stdout is not a TTY:

```
HARNESS FAILED: 3 blocking, 1 advisory (base: a1b2c3d, 4 files changed)

src/pkg/orders.py:42  process_order()
  [cognitive-complexity] 23 > 15
  Fix: extract the nested retry loop and the validation block into helpers.
  [S110] line 61: except Exception: pass
  Fix: catch the specific exception, or log and re-raise.

ADVISORY (review once, then fix or justify in your final message)
src/pkg/orders.py:88  _format_total()  is 91% similar to src/pkg/invoices.py:30 _fmt_total()
```

- Every rule ID maps to a one-line `Fix:` hint. Keep the hints in one table in `report.py`.
- Cap output at 40 findings and say how many were omitted, to protect agent context.
- `--json` emits the same findings as JSON for other tooling.

## 7. Check catalogue

Thresholds marked "tool default" match the tool's own default, which keeps the config explainable.

| # | Check | Tool | Threshold | Scope | Tier | Gate |
|---|---|---|---|---|---|---|
| 1 | Cognitive complexity | complexipy | ≤ 15 per function | Touched functions | Edit, gate | Block |
| 2 | Cyclomatic complexity | Ruff `C901` | ≤ 10 | Touched functions | Edit, gate | Block |
| 3 | Size and shape | Ruff `PLR09xx` | See 7.2 | Touched definitions | Edit, gate | Block |
| 4 | Architecture contracts | import-linter | All contracts kept | Whole project | Gate | Block |
| 5 | Dependency cycles | pyscn | 0 cycles | Whole project | Gate | Block |
| 6 | Coupling (CBO) | pyscn | ≤ 7 per class | Touched classes | Gate | Block |
| 7 | Cohesion (LCOM4) | pyscn | pyscn "high risk" band | Touched classes | Gate | Block |
| 8 | Dead code | vulture | See 7.6 | Touched definitions | Gate | Block |
| 9 | Exception hygiene | Ruff | 0 findings | Touched definitions | Edit, gate | Block |
| 10 | Type precision | mypy | `strict`, 0 errors | Touched definitions | Gate | Block |
| 11 | Suppressions | harness | No bare suppressions on added lines | Changed lines | Edit, gate | Block |
| 12 | Docstring presence | Ruff `D1xx` | Every public module, class, function and method | Touched definitions | Edit, gate | Block |
| 13 | Docstring consistency | pydoclint | 0 violations | Touched definitions | Gate | Block |
| 14 | Structural clones | pyscn | similarity ≥ 0.80 | Clone pairs with one side touched | Gate | Advisory |
| 15 | Mutation survival | cosmic-ray | ≤ 20% surviving on changed lines | Changed lines | CI job | Advisory at first |
| 16 | Churn × complexity | git, complexipy | Top 10 report | Whole project | Scheduled | Report only |
| 17 | Changelog reminder | harness | `src/` changed, `[Unreleased]` did not | Changed set | Gate | Advisory |

"Edit" tier means the check also runs in `--file` mode.

### 7.1 complexipy

- Config in `complexipy.toml`: max complexity 15, exclude `tests/**`.
- Use `--output-format json` and apply the harness scope filter, so behaviour matches the other tools. complexipy 9.0.0 also has native `--diff <ref>`, `--diff-only` and `--staged` flags and a snapshot feature; read `complexipy --help` and use them if they give identical results more simply.
- complexipy's `--suggest-refactors` output can feed the `Fix:` hint.

### 7.2 Ruff

Ruff carries four of the harness checks: complexity, size and shape, exception hygiene (7.7) and docstring presence (7.10). The **harness rule set** is:

`C901`, `PLR09`, `BLE001`, `S110`, `S112`, `TRY002`, `TRY203`, `TRY400`, `TRY401`, `D100`, `D101`, `D102`, `D103`, `D104`, `D106`

`E722`, `B904` and `B012` also belong to exception hygiene and are already active through the template's existing `E` and `B` selections.

```toml
[tool.ruff.lint.mccabe]
max-complexity = 10

[tool.ruff.lint.pylint]
max-args = 5
max-returns = 6
max-branches = 12
max-statements = 50
max-positional-args = 5

[tool.ruff.lint.pydocstyle]
convention = "{{ docstring_style }}"

[tool.ruff.lint.per-file-ignores]
"tests/**" = ["PLR0913", "PLR0915", "PLR0917", "D", "S110"]
```

In Ruff 0.17.6, `PLR0911`, `PLR0912`, `PLR0913`, `PLR0915`, `PLR0917` and `C901` are stable. `PLR0904` (public methods), `PLR0914` (locals), `PLR0916` (boolean expressions) and `PLR1702` (nested blocks) are preview-only. Check the status again under the template's pinned Ruff version. Do not turn on global preview mode; enable those four individually only if the pinned version supports selecting preview rules explicitly.

Because `select` is project-wide, existing projects would see these rules fire everywhere under `ruff check .`. So:

- `build.sh` keeps running `ruff check .` with the **original** rule set as the whole-project lint.
- The harness runs Ruff with `--extend-select <harness rule set> --output-format json` and applies the scope filter. Keep the rule list in `harness.toml`.
- For new projects generated from the template, put the harness rule set in `select` directly, since all code is new.

Make this a copier-time difference only if it stays simple; otherwise use the `--extend-select` approach everywhere.

### 7.3 import-linter

- Config in `.importlinter`, with `root_package = <project_name>`.
- A fresh project has no sub-packages, so ship one contract that passes trivially and documents the pattern, plus commented examples of `layers`, `forbidden` and `independence` contracts.
- Confirm `lint-imports` exits 0 on a freshly generated project. If import-linter rejects a config with no meaningful contract, ship a `forbidden` contract that stops the package importing from `tests`.
- `.importlinter` is project-owned: add it to `_skip_if_exists`.

### 7.4 pyscn

pyscn 1.33.2 has two relevant commands:

- `pyscn check --select deps --max-cycles 0 src/` gates dependency cycles.
- `pyscn analyze --json --select cbo,lcom,clones -o - src/` reports coupling, cohesion and clones. `pyscn check` has no CBO or LCOM threshold flags, so the harness parses this JSON and applies thresholds itself.

Thresholds:

- **CBO:** block above 7. That is the top of pyscn's default medium band (`[cbo] medium_threshold = 7`).
- **LCOM4:** block when pyscn classifies the class as high risk; report medium risk as advisory. Inspect the JSON on a sample class to find the field names and bands, and record the numeric values in `harness.toml`.
- Skip CBO and LCOM for dataclasses, `Protocol` classes, enums and exception classes if pyscn does not already do so. Those produce false positives.

Generate `.pyscn.toml` with `pyscn init`, then trim it. Disable the `[architecture]` layer validation: import-linter owns architecture, and pyscn's default layer names would produce confusing duplicate findings.

Do not use pyscn's complexity or dead-code gates. complexipy and vulture own those.

### 7.5 Clones (structural duplication)

From the same `pyscn analyze` run. Report a clone pair when similarity is ≥ 0.80 and at least one fragment is in a touched definition. Advisory only. See 7.11 for how advisories reach the agent.

### 7.6 vulture

A library's public API looks unused from inside the package, so confidence needs handling:

- Run `vulture src tests vulture_whitelist.py --min-confidence 60`. Including `tests` means tested public API counts as used.
- **Block** on findings with confidence ≥ 80 in touched code (unused imports, unused variables, unreachable code).
- **Block** on confidence-60 findings in touched code when the name starts with `_` (an abandoned private helper).
- **Advisory** for confidence-60 findings on public names.
- `vulture_whitelist.py` holds intentional exceptions and is project-owned (`_skip_if_exists`).

### 7.7 Exception hygiene (Ruff)

Ruff covers this without another tool. Rules and what each catches:

| Rule | Catches |
|---|---|
| `E722` | `except:` with no exception type |
| `BLE001` | `except Exception` or `except BaseException` that does not re-raise. This includes handlers that return a default and handlers that only log without exception info |
| `S110` | Handler body is only `pass` |
| `S112` | Handler body is only `continue` |
| `B904` | `raise` inside a handler without `from` |
| `B012` | `return`, `break` or `continue` inside `finally` |
| `TRY002` | Raising bare `Exception` instead of a specific class |
| `TRY203` | A `try` whose handler only re-raises |
| `TRY400` | `logging.error` in a handler where `logging.exception` keeps the traceback |
| `TRY401` | Redundant exception object in a `logging.exception` message |

Checked on Ruff 0.17.6: all of these are stable rules, and `BLE001` fires on both a broad handler that returns `None` and a broad handler that only calls `logging.warning`. Confirm the same under the template's pinned Ruff version.

Do not select the whole `S` or `TRY` families. `TRY300` and `TRY301` are style opinions that cause churn.

**Legitimate catch-all boundaries**, such as a CLI `main` or a task runner, use the standard suppression with a reason, which the suppression policy (7.9) already requires:

```python
except Exception:  # noqa: BLE001  # reason: top-level CLI boundary, error is logged and exit code set
```

No custom marker is needed.

Known gap: Ruff does not flag a *narrow* handler that returns a default, such as `except KeyError: return None`. That is often correct, so it is left to review.

### 7.8 mypy

Replace the individual flags with:

```toml
[tool.mypy]
python_version = "{{ min_python_version }}"
strict = true
warn_unreachable = true
disallow_any_explicit = true
enable_error_code = ["ignore-without-code", "redundant-expr", "truthy-bool"]
```

Keep the `tests.*` override, and relax `disallow_any_explicit` there too.

mypy needs the whole program, so run it on the package and filter the output to touched definitions. `build.sh` already runs whole-project mypy; for new projects that stays a full gate.

### 7.9 Suppression policy

Implemented in the harness, not by a third-party tool. On **added lines only**, block:

- `# type: ignore` without an error code.
- `# noqa` without a rule code.
- Any of `# type: ignore[...]`, `# noqa: ...`, `# pragma: no cover`, `# pragma: no mutate`, or a complexipy or pyscn inline ignore, unless the same line or the line above carries `# reason: <text>`.

Print a count of suppressions added in the diff even when all of them are justified, so the human reviewer sees it.

### 7.10 Docstrings: presence and consistency

Two tools, two jobs.

**Presence (Ruff).** `D100` to `D104` and `D106` require a docstring on every public module, class, method, function, package and nested class. Details:

- Names starting with `_` are not public, so private helpers are exempt.
- `D105` (magic methods) and `D107` (`__init__`) stay off. Constructor arguments are documented in the class docstring.
- Tests are exempt through `per-file-ignores`.
- Scope follows section 5. A missing module docstring (`D100`, `D104`) is reported on line 1, so it is in scope for new files and for existing files only when line 1 changes. Touching a public function with no docstring puts that function in scope.
- `convention` in `[tool.ruff.lint.pydocstyle]` must match the pydoclint style.

**Consistency (pydoclint).** Checks that a docstring's arguments, returns and raises match the signature.

```toml
[tool.pydoclint]
style = "{{ docstring_style }}"
arg-type-hints-in-docstring = false
check-return-types = false
check-yield-types = false
skip-checking-short-docstrings = true
exclude = "tests/"
```

Types belong in signatures, so the docstring type checks are off. Filter output to touched definitions. pydoclint also has a `--baseline` feature; the scope filter makes it unnecessary.

`skip-checking-short-docstrings = true` means a one-line summary satisfies both tools. That is intentional: a simple function needs a summary, not an `Args` section. Once a docstring has sections, they must be complete and correct. Set it to `false` to force full sections everywhere.

Neither tool can tell whether a docstring is useful. `AGENTS.md` covers that: a docstring states what the function does and any contract a caller needs, and does not restate the name.

### 7.11 Semantic duplication

Three layers, cheapest first:

1. **Prevention, in `AGENTS.md`:** before writing a new function or class, search the codebase for existing code with the same purpose, by name and by behaviour. State in the final message what was searched for.
2. **Detection, in the gate:** pyscn clone pairs (7.5), surfaced as advisories.
3. **Later, out of scope here:** an LLM review step or embedding search for cases with no structural similarity. Leave a short "future work" note in `docs/agent-harness.md`.

**How advisories reach the agent.** Advisories never fail lefthook or CI. In the Claude Code `Stop` hook, advisories block **once**: the first time the gate runs with advisories present, the hook blocks and tells the agent to either fix each one or justify it in its final message. On the retry, advisories are ignored. Agents without hooks see them when they run `scripts/check.sh`, as `AGENTS.md` requires.

### 7.12 cosmic-ray

`cosmic-ray.toml`:

```toml
[cosmic-ray]
module-path = "src/{{ project_name }}"
timeout = 30.0
excluded-modules = []
test-command = "pytest -x -q"

[cosmic-ray.distributor]
name = "local"

[cosmic-ray.filters.git-filter]
branch = "{{ default_branch }}"
```

`scripts/check.sh --mutation` runs:

```
cosmic-ray init cosmic-ray.toml .harness/mutation.sqlite
cr-filter-pragma .harness/mutation.sqlite
cr-filter-git --config cosmic-ray.toml .harness/mutation.sqlite
cosmic-ray exec cosmic-ray.toml .harness/mutation.sqlite
cr-report .harness/mutation.sqlite
cr-rate --fail-over 20 .harness/mutation.sqlite
```

`cr-filter-git` skips every mutation that is not on a line added or edited relative to the configured branch, which is what keeps this affordable. Confirm the exact arguments with `--help`; these commands exist in cosmic-ray 8.9.0 but the invocation above is untested.

- Runs as a separate PR job with a 20-minute timeout, and on demand locally.
- Starts as **non-required**. `docs/agent-harness.md` should say to make it required once the survival rate is stable.
- If the filter leaves zero mutations, pass.
- Surviving mutants are listed with file, line and the mutation applied, so an agent can write the missing assertion.

### 7.13 Hotspots (churn × complexity)

Report only. Built from tools already in the stack, with no extra dependency.

`scripts/hotspots.sh`:

1. Churn per file: count of commits touching each file under `src/`, from `git log --since=90.days --name-only`.
2. Complexity per file: total cognitive complexity from `complexipy --output-format json`.
3. Rank files by churn × complexity and write the top 10 to `reports/hotspots.md`, with both numbers and the three most complex functions in each file.

CI:

- A weekly scheduled workflow runs the script and uploads the report as an artifact.
- The PR job adds a complexity delta to the job summary using `complexipy --diff <base>`, non-blocking. Confirm the flag's output format with `complexipy --help`.

This gives the prioritisation signal. It does not give long-run trend graphs or a maintainability index; if those are wanted later, store each weekly report and diff them.

### 7.14 Changelog reminder

Implemented in the harness. If the changed set includes any file under `src/` and the `[Unreleased]` section of `CHANGELOG.md` has no added lines relative to the base, emit one advisory:

> `src/` changed but `CHANGELOG.md` has no new entry under `[Unreleased]`. Add one if a user of the package would notice this change; otherwise say in your final message that the change is internal.

It is advisory because refactors and internal changes need no entry. It follows the normal advisory path (7.11): it never fails lefthook or CI, and blocks the Claude Code `Stop` hook once.

Skip the check if `CHANGELOG.md` does not exist.

## 8. Claude Code adapter

Hooks are registered in `.claude/settings.json` and committed. Hook scripts are small Python files that read the JSON payload on stdin and call the harness. Use Python, not `jq`, to avoid an extra dependency.

Before writing these, read the current hooks reference at https://code.claude.com/docs/en/hooks and confirm the payload field names and exit-code behaviour described below.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "uv run python \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard_config.py" }]
      },
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "uv run python \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard_git.py" }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "uv run python \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/post_edit.py", "timeout": 15 }]
      }
    ],
    "Stop": [
      {
        "hooks": [{ "type": "command", "command": "uv run python \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/stop.py", "timeout": 120 }]
      }
    ]
  }
}
```

Check whether `uv run` adds noticeable latency per edit. If it does, call `.venv/bin/python` directly.

### 8.1 `post_edit.py` (PostToolUse)

- Read the edited file path from the payload. Ignore anything that is not a `.py` file under `src/` or `tests/`.
- Run `scripts/check.sh --file <path>`.
- On gate failure: print the findings to stderr and exit 2. The edit has already happened; exit 2 shows the findings to Claude.
- On pass: exit 0 with no output.
- On harness error (exit 3): exit 1 with a short message, so a broken harness never traps the agent.

### 8.2 `stop.py` (Stop)

`Stop` fires at the end of every response, including pure question-and-answer turns, so this hook must be cheap when nothing changed.

1. Compute a hash of the changed set (diff against base plus untracked files). If it equals the hash stored in `.harness/last-pass`, exit 0.
2. If there are no changed Python files, exit 0.
3. Run `scripts/check.sh`.
4. On pass with no advisories: store the hash, exit 0.
5. On failure, or on advisories, when the payload's `stop_hook_active` is **false**: print the report to stderr, followed by this instruction, and exit 2.

   > Fix the blocking findings in the definitions you changed. Do not refactor code you did not touch. For each advisory, either fix it or justify it in your final message. If a fix needs changes outside the code you touched, stop and explain instead.

6. On failure when `stop_hook_active` is **true**: do not block again. Exit 0 and emit JSON with a `systemMessage` telling the human that the harness still fails, with the finding count. Advisories are ignored on this pass.

### 8.3 `guard_config.py` (PreToolUse)

Stops an agent from relaxing a gate to get a green result. If the target path is one of the following, return a `permissionDecision` of `"ask"` with a reason, so the human is prompted:

`harness.toml`, `complexipy.toml`, `.pyscn.toml`, `.importlinter`, `cosmic-ray.toml`, `vulture_whitelist.py`, `.claude/**`, `scripts/harness/**`, `scripts/check.sh`, `lefthook.yml`

`pyproject.toml` is not guarded, because agents legitimately edit dependencies. CI covers it instead (section 10).

### 8.4 `guard_git.py` (PreToolUse)

Enforces the commit policy in `AGENTS.md` for Claude Code, so it does not depend on the agent remembering the instruction.

Read the Bash command from the payload. If it runs any of the following git subcommands, return a `permissionDecision` of `"ask"` with a reason, so the human approves or declines each one:

- **Changes what is staged or recorded:** `add`, `commit`, `push`, `tag`, `merge`, `rebase`, `cherry-pick`, `revert`, `am`
- **Can discard unreviewed work:** `reset`, `restore`, `checkout` with a path or `--`, `clean`, `stash`

Read-only commands (`status`, `diff`, `log`, `show`, `blame`, `merge-base`, `ls-files`, `rev-parse`) pass through untouched. The harness itself uses only those.

Match on the parsed command, not a naive substring: handle `git -C <dir> commit`, commands chained with `&&` or `;`, and avoid false positives such as `git log --grep commit`. When parsing is uncertain, ask.

The hooks reference describes an `if` field on handlers that filters by tool arguments, such as `"Bash(git *)"`. Use it to avoid starting Python for every non-git Bash call, if it behaves as documented.

## 11. `AGENTS.md`

Ship this text, templated where marked. Keep it short; agents read it on every session.

````markdown
# Agent instructions

This file is the canonical guide for any coding agent working in this repository.

## Commands

- `uv run ./scripts/check.sh` checks the code you changed. Run it before you say a task is done.
- `uv run ./scripts/check.sh --file <path>` checks one file quickly.
- `uv run ./scripts/build.sh` runs lint, format check, type check, tests and the harness. This is what the commit hook and CI run.
- `uv run ./scripts/check.sh --mutation` runs mutation testing on your changed lines. Slow; run it when you add or change tests.

## The working loop

1. Before writing a new function or class, search for existing code that already does the job, by name and by behaviour. Reuse or extend it. Say in your final message what you searched for.
2. Make the change, with tests.
3. Run `scripts/check.sh`. Fix every blocking finding.
4. For each advisory finding, fix it or explain in your final message why it stands.
5. Run `scripts/build.sh`. Only then report the task as done.

## Scope of refactoring

The harness checks only definitions you changed. When you touch a function or class, you own its findings, including ones that were there before you.

- Do fix findings in functions and classes you changed.
- Do not refactor code you did not need to touch for the task.
- Do not start codebase-wide clean-ups, even if `check.sh --all` shows problems.
- If fixing a finding needs changes beyond the definitions you touched and their direct callers, stop. Report the finding, what the fix would involve, and let the human decide.

## Never do these to get a passing result

- Edit thresholds or harness config (`harness.toml`, `complexipy.toml`, `.pyscn.toml`, `.importlinter`, `.claude/`, `scripts/harness/`, Ruff or mypy settings).
- Add `# noqa`, `# type: ignore` or `# pragma: no cover` without a specific code and a `# reason:` comment. Suppression is a last resort.
- Delete, skip or weaken a test.
- Split a function into meaningless fragments to get under a limit. Extract helpers that have a name and a purpose.
- Bypass hooks with `--no-verify`.

If you believe a threshold or rule is wrong for a case, say so and propose the change. Do not make it.

## Code rules the harness enforces

- **Complexity:** cognitive complexity ≤ 15 and cyclomatic ≤ 10 per function. At most 5 arguments, 12 branches, 6 returns, 50 statements.
- **Architecture:** imports must satisfy the contracts in `.importlinter`. No import cycles.
- **Classes:** keep coupling low and give each class one responsibility.
- **Dead code:** remove helpers, imports and variables you stop using. Do not leave commented-out code.
- **Exceptions:** catch specific exceptions. Never swallow one. Re-raise with `raise ... from err`. Do not return a default from a broad handler to hide a failure. A function that must catch everything, such as a CLI entry point, carries `# noqa: BLE001  # reason: <why>` on the handler.
- **Types:** full annotations, no explicit `Any`.
- **Docstrings:** required on every public module, class, function and method, in {{ docstring_style }} style. Say what it does and what a caller must know; do not restate the name. A one-line summary is enough for a simple function. If you document arguments, returns or raises, they must match the signature. Types go in the signature, not the docstring.
- **Tests:** assert on behaviour and outcomes. A test that only executes code without asserting anything is not a test. Mock at boundaries, not internals.

## Readability

- Names say what a thing is for.
- Comments explain why, never what the next line does.
- Prefer the simple direct solution. No speculative abstractions, no single-implementation interfaces, no unused configuration options.

## Git and commits

- Do not stage, commit, push, tag, stash or discard changes unless the user explicitly asks you to. Leave every change unstaged in the working tree for the user to review and commit.
- A request to commit covers that commit only. It is not standing permission for later ones.
- Read-only git commands (`status`, `diff`, `log`, `show`, `blame`) are always fine.
- At the end of every task, propose a commit message in Conventional Commits format (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`). If the work would be clearer as several commits, propose each message with the files it covers.
- The body of a `fix:` message has three lines: `Symptom:`, `Cause:`, `Fix:`.

## Recording changes

- For any change a user of this package would notice, add one line under `[Unreleased]` in `CHANGELOG.md`, in the matching category (Added, Changed, Deprecated, Removed, Fixed, Security). Describe the effect, not the code edit.
- Skip refactors, tests and tooling changes.
- Never edit released sections or change the version number.

## Fixing bugs

1. Before debugging, search `docs/troubleshooting.md` and `git log --grep` for the error message or symptom.
2. Write a test that reproduces the bug and fails. Then fix the bug. The test's docstring states the symptom.
3. If the lesson can be enforced by a test, lint rule or import contract, add that instead of a note.
4. Add an entry to `docs/troubleshooting.md` only if the cause was not apparent from the error, or the problem could recur. Follow the format at the top of that file, and quote the exact error text.
5. If you find an entry that describes code which no longer exists, remove it.
6. Record a design decision that future work must respect as an ADR in `docs/adr/`, copied from `0000-template.md` and numbered in sequence.

## Final message

State: what changed, what you searched for before adding new code, the result of `scripts/build.sh`, any advisory you left and why, any finding you could not fix within scope, and your proposed commit message or messages.
````

## 14. Working method for the implementing agent

Work in this order. Do not stage or commit anything in the template repository unless the owner asks; leave changes unstaged and, at the end of each step, propose a Conventional Commits message for it:

1. Scope model and `check.sh` skeleton with Ruff and complexipy only. Get scenarios 1, 2, 3, 11, 12 and 13 passing first; the scope model is the part most likely to be subtly wrong.
2. Remaining gate runners, one at a time, each with its scenario.
3. `AGENTS.md`, `CLAUDE.md`, Claude Code hooks.
4. lefthook and CI changes.
5. Mutation job and hotspots.
6. Copier questions, conditional generation, `_exclude`, `.gitignore`.
7. `docs/agent-harness.md` and README sections.
8. Full smoke run.

Rules:

- Where this brief says "confirm" or quotes a flag, check `--help` or the tool's docs before relying on it. Tool versions move quickly.
- The harness code itself must pass the harness.
- If a tool cannot do what this brief assumes, do not invent a workaround silently. Implement the closest behaviour, mark it in the docs, and list it in your final report.
- Do not change existing template behaviour beyond what this brief describes.

Final report should list: what was built, each deviation from this brief and why, each assumption that turned out wrong, and measured gate timings.
